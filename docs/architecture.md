# Architecture

## Overview

edwardjensen.net is a statically generated (SSG) Astro site. All content is fetched from the
**Cloudflare KV content relay** at build time — never from Payload CMS directly — pre-rendered
to HTML, and deployed to Cloudflare Workers as static assets.

`astro.config.mjs` sets `output: 'static'` with the Cloudflare adapter installed. The adapter
is present for future SSR capability; individual pages can opt into on-demand rendering with
`export const prerender = false`, but none currently do.

Interactive features (navigation, photo gallery modal) are handled by Preact islands — small JavaScript components that hydrate on the client only where needed.

## Content Fetching

**Source:** Cloudflare KV content relay at `contentrelay.edwardjensen.net` (public, key-authenticated).

The API client lives in `src/lib/payload.ts`. Key aspects:

- **Auto-pagination:** Each collection fetcher loops through all pages (PAGE_LIMIT = 100 per request) until all documents are retrieved.
- **Retry with backoff:** Failed fetches are retried up to 5 times with delays of 1s, 2s, 4s, 8s, 16s. A build fails loudly rather than silently rendering a site with missing content.
- **Build-time caching:** A module-level `Map` ensures each collection is fetched only once per build, even if multiple pages reference the same data.
- **Permalink helpers:** `postPath()`, `workingNotePath()`, `photoPath()`, `historicPostPath()` generate URL paths from document slugs and dates.
- **Environment config:** `CONTENT_RELAY_URL` points to the relay base URL — the client appends `/v2` itself. `CONTENT_RELAY_READ_KEY` is sent as the `X-Read-Key` header on all requests.

Site-wide constants (canonical URL, title, feed limits, page sizes, search debounce) live in
`src/config.ts`, not in the client.

### Content Types

| Type | Collection Slug | URL Pattern |
|------|----------------|-------------|
| Blog posts | `posts` | `/posts/YYYY/YYYY-MM/slug` |
| Working notes | `working-notes` | `/notes/YYYY-MM-DD/slug` |
| Photography | `photography` | `/photos/YYYY/YYYY-MM/slug` |
| Historic posts | `historic-posts` | `/archive/posts/slug` |
| Pages | `pages` | `/slug` (catch-all route) |

### CMS Data Shape

TypeScript interfaces for all content types are defined in `src/types/payload.ts`. Key patterns:

- **Pre-rendered HTML:** The CMS provides `contentHtml` with rendered rich text.
- **Embedded notes:** Blog posts may contain `<!-- embed:ID -->` placeholders in their HTML, with corresponding `blocks` array entries. The page template resolves and inlines these.
- **Image metadata:** Featured images include `url`, `alt`, `width`, `height`.
- **EXIF data:** Photography entries include camera model, lens, aperture, shutter speed, ISO, focal length, and capture date.
- **Location data:** Photography entries may include latitude, longitude, location label, and precision level.

## Page Routing

Astro's file-based routing in `src/pages/`:

- **Dynamic routes** use `getStaticPaths()` to generate all pages at build time.
- **Catch-all routes** (`[...slug].astro`) handle CMS-managed pages and nested URL patterns.
- **Pagination** uses Astro's built-in pagination via `getStaticPaths()` with `paginate()`.

## Layouts

Three layout levels:

1. **BaseLayout** — HTML shell, `<head>`, SEO meta, skip link, header nav island, photo modal, footer.
2. **ContentWrapper** — Extends BaseLayout with standard article container styling.
3. **LandingPage** — Extends BaseLayout with a centered intro section and named `sections` slot.

## Interactive Islands

Preact components in `src/islands/` are hydrated on the client:

- **HeaderNav** (`client:load`) — Sticky header with scroll-hide, desktop dropdowns, mobile hamburger menu, keyboard support.

Vanilla JavaScript handles:

- **Photo gallery** (`public/assets/js/photo-gallery.js`) — Modal with URL routing, EXIF display, Google Maps, keyboard navigation, browser history.
- **Search** — Lunr.js against a build-time JSON index. The index is generated by the
  `src/pages/search-index.json.ts` endpoint; the search logic itself is written inline in
  `src/pages/search/index.astro` and `src/pages/404.astro` (duplicated between the two).
  Lunr is loaded from cdnjs via an `is:inline` script tag, not bundled — it is the one
  external runtime dependency on the site.

## Supporting Workers

Three Cloudflare Workers live in this repo, each in `cloudflare-workers/`, and run alongside the main site:

- **hi-redirector** — Short URL redirect service. Fetches redirect mappings from a CMS globals endpoint.
- **maps-proxy** — Proxies Google Maps Static API requests, keeping the API key server-side.
- **stream-proxy** — Proxies Cloudflare Stream embeds.

A fourth worker, **content-relay**, is what this site actually reads content from (see [Content Fetching](#content-fetching) above) — but its source lives in the `edwardjensencms-payload` repo, not here, since it's deployed and owned alongside the CMS that populates it.

## Build Pipeline

```
Payload CMS  ──push on publish──▶  Cloudflare KV content relay
                                            │
                                            ▼
  src/lib/payload.ts  (fetch + retry + cache all content)
        │
        ▼
  src/pages/*.astro   (generate static pages via getStaticPaths)
        │
        ▼
     dist/            (Astro build output)
        │
        ▼
  Cloudflare Workers  (wrangler deploy)
```

## Deployment Model

```
PR → build + a11y checks (required gate)
  │
  ▼
main → staging worker (automatic)
  │
  ▼
vX.Y.Z tag → production worker (www.edwardjensen.net)
  │
  ▼
CMS webhook → freshness gate → rebuild from latest tag with fresh content
```

**The freshness gate is a build-blocking step, not a courtesy wait.** A CMS publish arrives as
a `repository_dispatch` carrying `client_payload.relayVersion`. Before building, the republish
workflows poll `GET /v2/{collection}` — the *list* endpoint, the exact KV key the build will
read, not `/v2/meta/`, which is a separate key with its own independent 60s edge cache — until
the reported `version` is at least `relayVersion`. If that hasn't happened within 180s the
step **fails the build**. Re-run the workflow once the relay is healthy.

A dispatch with no `relayVersion`, or a relay worker reporting no `version`, degrades to the
older `meta.updatedAt` comparison with a warning. `workflow_dispatch` runs skip the gate
entirely — a manual republish is an explicit human decision.
